# 数据库启动迁移

启动入口为 `database.AutoMigrate()`，由 `GetDB()` 和 `cmd/hephaestus-migrate` 调用。
步骤清单位于 `pkg/database/migration_steps.go`；本目录 `runner.go` 负责执行顺序、事务和 PostgreSQL advisory lock。

## 根据数据库迁移记录升级

所有发布版本都注册完整的历史迁移步骤，Web 和桌面端采用同一规则。是否执行由数据库中的 `schema_migrations` 完成记录决定，不再以当前程序版本设置上限。用户可以从旧版本直接升级到新版，无需逐个安装中间版本。

- 没有完成记录：按顺序执行。步骤内部检查旧表、旧字段及数据，兼容新库与已经转换过但没有记录的旧库。
- 成功完成：写入完成记录，后续启动跳过。
- 执行失败：事务回滚，不写入完成记录，下次启动重试。
- 部分完成（`applied=false, err=nil`）：提交部分成果，停止本轮且不记录完成，下次启动继续。
- 旧版本重复执行但未记录的历史步骤会安全补跑一次；已有完成记录保留。
- `db_collect_data_migration_version` 仅用于转换报告和并发锁，不作为迁移完成依据。
- Agent 节点继续使用原有 schema 检查流程，不负责启动迁移。

## 新库建表及正常表结构更新

`schemaModels()` 必须包含所有当前使用的模型，包括子域名结果表。`schema_sync:<版本+模型指纹>` 由 `schema_migrations` 记录：

- 指纹包含 `Version`、`DesktopVersion` 和模型字段、类型、`gorm` tag。
- 新库自动创建当前模型需要的表；发布版本或模型变化后同步一次。
- 同版本、同模型再次启动跳过同步；每次同步只保留当前指纹记录。
- 旧主键、漏洞 ID、计划任务转换以及旧子域名结果外键解除先于表结构同步；其余数据回填在同步之后执行。
- 生产启动入口须先注册 `BeforeAutoMigrate` 计划任务转换；未注册时不生成该步骤的完成记录。

## 执行与维护规则

1. 步骤 ID 永久唯一。新增工作使用新 ID，不能修改已完成步骤并期望旧库重新执行。
2. 默认每步在独立事务中执行。连接级语句使用 `OutsideTx`，步骤自身负责幂等和安全重试。
3. 历史步骤必须幂等；补跑不得重复数据或覆盖已转换内容。
4. 步骤只使用传入的 `*gorm.DB`，不要调用尚在初始化的 `GetDB()`。
5. 验证新库、旧库直接升级、已完成记录、重复启动、失败重试、数据保留及并发安全。
