# 数据库启动迁移

启动入口为 `database.AutoMigrate()`，由 `GetDB()` 和 `cmd/hephaestus-migrate` 调用。
步骤清单位于 `pkg/database/migration_steps.go`；本目录 `runner.go` 负责执行顺序、事务和 PostgreSQL advisory lock。

## 历史迁移：只判断当前运行版本

这批历史兼容步骤（`0001`–`0013`，包括旧计划任务转换）按当前进程的运行模式选择版本：

| 运行模式 | 使用的程序版本 | 执行历史迁移的条件 |
| --- | --- | --- |
| Web 服务端 | `version.Version` | ≤ `v0.5.6` |
| 桌面客户端 | `version.DesktopVersion` | ≤ `v3.3.2` |

- 采用语义版本比较，包含边界版本；不根据操作系统或数据库类型猜测运行模式。
- 范围内每次启动都执行这批幂等历史步骤，`Repeatable` 步骤忽略已有完成记录，也不新增完成记录。
- 高于上限时不注册这批历史步骤，即使数据库没有迁移记录，也不会自动补跑。
- `db_collect_data_migration_version` 仅保留转换报告和并发锁用途，其 `version` 不参与执行条件判断。
- Agent 节点继续使用原有 schema 检查流程，不负责启动迁移。
- 固定上限不会随发布版本自动提高。新增迁移需要明确适用范围，不应直接归入这批历史步骤。

## 新库建表及正常表结构更新

这些工作不受历史迁移版本上限限制。`schema_sync:<版本+模型指纹>` 仍由 `schema_migrations` 记录：

- 指纹包含 `Version`、`DesktopVersion` 和模型字段、类型、`gorm` tag。
- 新库自动创建当前模型需要的表。
- 发布版本或模型变化后同步一次；同版本、同模型再次启动跳过表结构同步。
- 每次同步删除旧的 `schema_sync:*` 记录，只保留当前指纹。
- 旧计划任务转换已从表结构同步中分离，受历史版本上限限制。

## 执行与维护规则

1. 步骤 ID 保持唯一；新增工作使用新 ID。此次既有历史步骤的调度方式已改为当前版本控制。
2. 默认每步在独立事务中执行，失败回滚。连接级语句使用 `OutsideTx`，步骤自身负责安全重试。
3. `applied=false, err=nil` 会提交部分成果并停止本轮，下次符合版本范围的启动重试。
4. 历史步骤必须幂等；重复执行不得重复数据或覆盖已转换内容。
5. 步骤只使用传入的 `*gorm.DB`，不要调用尚在初始化的 `GetDB()`。
6. 修改时验证 Web/桌面的低于、等于、高于边界，以及高版本建表、重复执行、失败回滚和并发安全。
